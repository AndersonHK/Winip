# Checkpoint 09 — responsive images, Markdown and eager opening

Release **0.2.2**, 2026-09-14, following committed 0.2.1 (`0abaf69`). Development executable: `x64/Release/Winip-dev-24.exe`. Installer: `Artifacts/packaging/Winip-0.2.2-x64.msi`. Exact evidence and identities are in the validation summary (local archive: `Artifacts/archive/validation/checkpoint09-summary.json`; not distributed).

## Behavior and ownership

Rendered Markdown now wraps to the current page width. PNG/JPEG images resolve from base64 data URLs, notebook attachments (including percent-encoded names), and paths relative to the notebook. The private-notebook screenshot's missing images were data URLs previously reduced to alt labels; this was a missing Markdown image path, not a new PNG codec. Missing/remote/unsupported images retain an explicit diagnostic, and their original notebook data remains intact. No HTTP image fetch or notebook execution occurs on opening.

Images fit both the available width and viewport height by default. Double-click switches to natural display size with normal notebook scrolling and the draggable horizontal cell bar; double-click again restores fitting. Output metadata dimensions remain honored. Original-resolution pixels and profiles are retained, including after fitting, DPI changes and toggles. Presentation changes do not dirty the notebook.

The owner caught an occupied-height bug missed by the initial checks: Markdown ending with an image reserved twice the displayed image height. `MarkdownInline` forced a break after the final object, creating an empty DirectWrite line with the same height. Dev-24 uses a permitted break after the image; explicit parser paragraph separators remain. A failing-before/passing-after regression now checks following-cell movement, terminal images, multiple images, surrounding text, narrow widths and repeated toggles. The private-notebook layout inspection confirms all seven Markdown images now occupy their displayed height (for example, 650 rather than 1300 DIPs). The final app-owned private-notebook and fixture media probes, code-image probe and 320-step Markdown resize probe pass; Release/Debug and all 304 GPU fidelity comparisons also pass after this fix.

`Markdown` separates parsed content/images from immutable shaped layouts. `MarkdownInline` provides image extents to DirectWrite; the renderer paints the original source through its GPU image path. `NotebookFlow` prepares coherent heights/positions and preserves the visible cell's scroll anchor. Layout is published with its completed frame and matching revision, retaining source/edit history. Height-only changes and widths exceeding a short heading's measured natural extent reuse the same layout. Narrow widths still reflow. Pretext was reviewed; no browser library or independent-character shaping approximation was introduced.

The loader resolves all supported images and prepares initial responsive geometry before publication. It also prepares bounded full-resolution textures through `ImageUpload`, using thread-safe D3D11 device creation without touching the render worker's immediate/D2D context. D2D wraps these textures instead of uploading pixels on first scroll. A 1 GiB prepared-texture budget covers the entire private-notebook sample. The existing bitmap cache remains the hardware fallback for live output, unsupported sharing, resource pressure and larger documents. These bounds and the driver-controlled residency limitation are recorded in [Architecture](Architecture.md).

New image references introduced by editing resolve on the document worker and apply only to matching cell/source identities. That asynchronous edit-completion path does not defer file-open preparation into browsing. There are no new idle polling timers in normal operation.

## private-notebook loading stretch

Only the workspace copy under `Artifacts/benchmark-private` was used. Its SHA-256 is `0fe4719027e49fbf783eee7003aa995ddc56d550f037f9ed8345788694943b98`: 194,675,788 file bytes, 99 cells, 19 code-output images and 7 Markdown images, totaling 618,988,200 decoded pixel bytes. No cells were executed and the original network notebook was not changed.

The CPU preparation benchmark performs full parsing, model construction, image decoding and initial text preparation. It does not time first presentation. Three before/after trials of the same 0.2.2 functionality measured median **3246.20 ms → 3078.36 ms (5.2%)**. The optimization removes large JSON/base64 temporary copies and the extra base64 sizing scan. Relative image files use a bounded bulk read. Nothing is omitted or decoded on demand to obtain the improvement.

The separate GPU-ready benchmark also fits a 1600×900 DIP viewport and creates a new benchmark device plus all 26 original-resolution textures. Its median total is **3420.94 ms**, including median **185.80 ms** texture preparation. These totals are deliberately not presented as an apples-to-apples speedup over a CPU-only number. The application normally already has its render device when opening a file. The owner's preference is explicit: spend the required preparation time during opening, rather than moving stalls into scrolling.

The first full private-notebook sweep exposed the 512 MiB cache limit: the newly displayed Markdown images caused eviction and repeated upload spikes, including roughly 20–38 ms frames. Loader-prepared textures retain the whole sample within the new bounded pool. A subsequent first/warm image sweep remained below 3 ms per measured scroll frame; startup and DPI transitions are separate samples. The dev-23 private-notebook probe prepared all 26 textures, passed fit/full/fit and 200% DPI, performed 30 resizes during reload (maximum native transaction 3.21 ms), and recorded three idle intervals with zero frames and zero measured CPU. After the terminal-image height fix, the final dev-24 timing probe again passed all 26 uploads and geometry checks, with 29 reload resizes (maximum 3.35 ms) and three zero-CPU/zero-frame idle intervals. The CPU optimization timings above precede that final line-break correction. This is host evidence, not proof of universal 160 Hz pacing.

## Regression evidence and intermediate failures

Release and Debug model suites pass. Image-source resolution, Unicode wrapping, unchanged-layout reuse, image toggles, original-data preservation, consistent cell positions and asynchronous edits are covered. The real kernel suite passes Hello World, shared state, errors, interruption/restart, Pillow, IPython JPEG and Matplotlib. No packages, Python installation or user associations were changed.

All **144 image fidelity comparisons** pass with original and loader-prepared textures: PNG/JPEG, ICC, transparency, SDR/FP16 HDR, fractional/200% DPI, full/half-size and repeat use. The existing **160 text-cache comparisons** pass unchanged.

The resize audit found unnecessary short-heading layout invalidation in an intermediate candidate: the visualization fixture's raster misses rose from 111 to 967. Reusing shaped layouts when the viewport cannot change line breaks reduced this to 201, including initial/narrow-width variants. Functionality and live resizing were retained. In the 24-run baseline/dev-23 matrix all frame/allocation checks passed, with 313 presentations per workload and ordinary UI maxima below 0.06 ms. This matrix precedes the final terminal-image correction; the affected Markdown image workload was retested on dev-24. Process CPU medians vary in both directions and remain coarse host measurements:

| --- | ---: | ---: |
| Images | 437.50 | 515.63 |
| 1000 cells | 671.88 | 546.88 |
| Long lines | 531.25 | 468.75 |

An intermediate dev-22 image probe failed its fresh execution-count assertion. Its log did not record the actual counter. Inspection found unsynchronized probe reads during layout publication; the probe now holds a stable document snapshot, and unchanged frames no longer rewrite the document pointer. Five consecutive image runs then passed fresh/reopened counts, live images, HDR/DPI, save/reopen and idle gates. The original run also contains key-down/character messages the probe never generates, so unintended input is a plausible contributor; the original failure's precise cause is not proven. A subsequent navigator run failed capture while also recording unsolicited keyboard input. Failed evidence is retained rather than relabeled as passing.

The first sandboxed real-kernel run failed while securing its disposable connection file (`SetFileSecurity`, access denied). The outside-sandbox retry initially used a relative root and correctly failed the absolute-path check; the corrected invocation passed. No thresholds or application permissions were relaxed.

Later dev-23 image repeats failed only idle accounting (15.625 and 31.25 ms, with zero extra frames). Three fixed alternating candidate/baseline trials added thread/message diagnostics: all candidate trials passed, with nine intervals of zero process/UI/render/loader CPU and zero frames; one baseline trial failed with six extra frames. These results do not establish the precise cause of the earlier fluctuations. Dev-24's private-notebook capture run also failed idle accounting (46.875/15.625/15.625 ms and 0/0/1 frames), while its geometry/capture checks completed. Its subsequent no-readback private-notebook, fixture-media and code-image runs passed unchanged idle gates. Captures and failures are retained separately from accepted timing evidence.

## Bounds and handoff

PNG/JPEG and the existing 16384-pixel decoder/device bounds remain. Animated/high-depth/other formats, remote images, full Markdown math/tables/HTML and arbitrary huge-cell editing are not completed by this patch. The prepared GPU pool is bounded and cannot guarantee residency or stall-free browsing beyond its capacity or on every driver. Full Windows 7–11, device-loss/low-VRAM, physical HDR and sustained refresh-deadline certification remain outstanding.

The MSI uses version 0.2.2 with the established repair/update identity and payload layout. Read-only MSI/ICE and 0.2.1 component-compatibility validation pass. The owner had installed an earlier local 0.2.2 candidate and explicitly requested the corrected files. An initial silent recache was refused with MSI 1625 because elevation was required; the normal UAC-authorized `/fvamus` repair completed with exit 0. The installed executable SHA256 matches the final validated payload, and the user's settings SHA256 is unchanged. This refresh of an unreleased local candidate does not establish a policy of changing already-distributed release contents. Fresh installation, cross-version live upgrade, association behavior and slower-machine visual acceptance remain separate manual checks. The reported private notebook was never executed.
